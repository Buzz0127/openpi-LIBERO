# π0-LIBERO 失败分析：从超时标签到行为证据

## 1. 分析目的

完整四-suite评测得到 1,845/2,000（92.25%）。结构化结果中的155个失败都被
评测器记录为 `max_control_steps`，但这个标签只说明任务没有在步数上限内满足
成功谓词，不能解释模型具体在哪个控制阶段失败。

本文以表现最弱的 `libero_10` task 8 为案例，把结构化统计、视频观察、行为
分类和实验假设分开记录。任务语言为：

> `put both moka pots on the stove`

task 8 的结果是13/50（26.00%）；平均控制步为495.14，P95为520，平均策略
请求数为99.12。37个失败都达到520步上限，且没有 Python、MuJoCo、WebSocket
或评测器系统异常。

观察来自项目所有者本地保存的原始证据。

## 3. 分析方法

### 3.1 控制阶段

每个 episode 按五个阶段观察：

1. 接近第一个 moka pot；
2. 抓取第一个 pot；
3. 搬运并放置第一个 pot；
4. 切换到第二个 pot；
5. 抓取并放置第二个 pot。

如果某个阶段没有发生，标记为“未进入”，不根据最终失败标签反推模型内部原因。

### 3.2 观察与推断分离

“夹爪没有把 pot 稳定抬离桌面”是视频可见事实；“模型没有识别 pot”是内部
原因推断，不能只凭第三人称视频证明。本文优先记录前者。

### 3.3 抽样

先用成功 state 5 作为对照。失败样本包含：

- 预先按排序位置选择的分层样本：states 0、16、31、48；
- 补充观察样本：states 20、39。

因此共有6个不重复失败样本。分层抽样减少只挑选明显案例的偏差，但6/37仍然
不是全部失败的完整标注，不能直接外推总体比例。

## 4. 成功对照：state 5

state 5 在486个控制步、98次策略请求后成功。人工观察为：

- 第一个 pot 已稳定放到炉灶上；
- 第二个 pot 已进入正确目标区域；
- 第二个 pot 尚未表现出完整、稳定的人类式释放动作，episode 已结束。

这说明环境会在某一步首次满足成功谓词时令 `done=True`。基准成功不额外要求
机械臂回到安全位置、远离物体或保持若干秒稳定。因此必须区分：

```text
环境成功谓词首次成立 != 模型完成完整收尾动作
```

## 5. 六个失败样本

| State | 第一物体结果 | 第二阶段 | 重复控制 | 首要失败 | 后续失败 |
| ---: | --- | --- | --- | --- | --- |
| 0 | 搬运到炉灶后倾倒 | 未完成第二个 pot | 未标注 | 放置不稳定 | 未能恢复并完成第二阶段 |
| 16 | 未形成稳定抓取 | 未进入 | 是 | 第一物体抓取失败 | 重复抓取、无进展 |
| 20 | 未形成稳定抓取 | 未进入 | 是 | 第一物体抓取失败 | 重复控制、无进展 |
| 31 | 未形成稳定抓取 | 未进入 | 否 | 第一物体抓取失败 | 阶段停滞，没有有效恢复 |
| 39 | 抓取失败并碰倒物体 | 未进入 | 否 | 第一物体抓取失败 | 未进入第二阶段 |
| 48 | 未形成稳定抓取 | 未进入 | 否 | 第一物体抓取失败 | 无有效重试或阶段转换 |

state 0 的“重复控制”没有完成标注，因此既不计入“是”，也不自动计入“否”。

## 6. 样本内初步统计

- 第一物体抓取失败：5/6（83.3%）；
- 第一物体放置不稳定：1/6（16.7%）；
- 成功完成第二个 pot：0/6；
- 明确出现重复控制：2/6（33.3%，保守计数）；
- 系统异常：0/6。

这些百分比只描述已标注的6个失败样本。严谨表述是：

> 在已检查的6个 task 8 失败样本中，失败都发生在第一物体的抓取、放置或其后
> 的恢复阶段，并阻断第二物体的完成；其中5个样本的首要失败是第一物体抓取失败。

不能据此直接声称“task 8 的37个失败中83.3%都是抓取失败”。

## 7. 初步失败树

```text
task 8 失败
├── 第一物体抓取失败
│   ├── 重复尝试、无进展
│   ├── 碰撞并改变物体姿态
│   └── 无有效重试或阶段转换
├── 第一物体放置失败
│   └── 到达炉灶后倾倒或失稳
├── 异常恢复失败
│   └── 场景状态恶化后没有恢复到可执行状态
└── 阶段转换失败
    └── 没有进入第二物体的抓取与放置
```

闭环每5步重新观察和规划，说明策略持续使用环境反馈；但闭环本身不保证策略
具备显式失败检测、异常恢复或任务阶段管理能力。

## 8. 待验证假设

### H1：第一物体抓取是 task 8 的主要瓶颈

依据：样本中5/6以第一物体抓取失败为首要失败。

验证方法：标注全部37个失败视频的首个失败阶段，再计算完整分布。只有完成全量
标注后，才能报告 task 8 的抓取失败比例。

### H2：失败后的恢复能力弱于正常轨迹执行能力

依据：物体倾倒、抓取失败或状态恶化后，样本没有恢复并完成第二物体；部分轨迹
陷入重复控制。

验证方法：对全部失败标记“是否重新建立有效抓取”“是否从异常姿态恢复”“是否
切换到第二物体”，区分没有恢复尝试和尝试后仍失败。

### H3：执行5步再规划可能放大接触阶段的误差

依据：已有视频出现抓取附近重复控制、碰撞和放置失稳。但当前观察不能证明
`replan_steps=5` 是原因。

验证方法：在保持 checkpoint、seed、initial states、控制步上限和其他环境配置
不变的诊断实验中，对同一组失败 states 比较 `replan_steps=5` 与更短执行窗口。
该实验必须单独报告，不能回写或替换本次固定协议的2,000-episode结果。

### H4：单纯提高控制步上限不会解决全部失败

依据：部分失败长时间没有有效进展，继续增加步数可能只延长重复控制。

验证方法：先使用动作和视频标注区分“接近成功但时间不足”与“早期失效后无
进展”。只有前一类适合进行更长步数的诊断；不能在观察结果后修改原 benchmark
上限并把新结果与原结果混合。

## 9. 可选研究支线

以下工作用于进一步研究 task 8 的失败分布，不阻塞部署演练、项目封版或当前
2,000-episode 结果的发布。

### 无 GPU 阶段

1. 标注 task 8 全部37个失败；
2. 使用固定枚举字段记录首要阶段、后续阶段、重复控制、物体倾倒和完成的子目标数；
3. 进行一次复核，解决“没有重试”与“有重试但失败”等容易混淆的标签；
4. 输出全量失败类型分布，并选择每类一条代表视频。

### 可选 GPU 诊断阶段

只有全量视频标注支持明确假设后，再对少量固定 states 做受控对照。任何新实验都
必须重新执行共享 GPU 基线采样、单卡映射与保护器启动，并与原2,000-episode
基准结果分目录保存。

## 10. 可复述结论

> 完整评测发现 LIBERO-10 task 8 只有26%成功率。我没有把37个失败统一解释成
> “超时”，而是对成功轨迹和分层失败样本按抓取、放置、恢复与阶段转换进行视频
> 标注。初步6个失败样本中，5个首先发生第一物体抓取失败，所有样本都未完成第二
> 物体；部分轨迹还出现重复控制。这个结果提示第一物体操作与异常恢复可能是主要
> 瓶颈，但样本不足以代表全部37个失败，因此下一步应先完成全量无 GPU 标注，再
> 设计受控重规划窗口实验。
